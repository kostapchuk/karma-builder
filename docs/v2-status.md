# V2 — состояние на 17 августа 2026

Что построено по [плану V2](./v2-reviews.md), чем реализация от него отличается
и что осталось сделать руками.

Документ описывает **фактическое** состояние кода. План остаётся замыслом
и под реализацию не переписывался — расхождения перечислены явно, как и в
[v1-status.md](./v1-status.md).

## Расхождения с планом

Семь отступлений. Первые три меняют схему, остальные — механику.

**1. В `users` добавлены агрегаты: стрик, счётчики, бейджи.**
План описывал только карму и уровень. Но экраны V2 показывают стрик и бейджи
(`/api/me`, профиль друга), а считать их запросом по всей истории на каждый
вызов дороже, чем держать в строке юзера. Раскладка повторяет `state` из V1:
`streak_current`, `streak_longest`, `last_deed_date`, `deed_count`,
`category_counts`, `badges`.

**2. У дела появился `local_date`.**
Worker живёт в UTC, «день» для стрика и heatmap — календарный день
пользователя. Без отдельной колонки они разъезжались бы на границе суток.
Клиент присылает свой день вместе с делом.

**3. Флаг импорта — на сервере, а не в `meta` CloudStorage.**
План предлагал пометить `meta` ключом `imported`. Вместо этого стоит
`users.legacy_imported_at`. Причина: флаг на устройстве не защищает от второго
устройства — пользователь открыл бы V2 на планшете и импортировал бы всё ещё
раз. Серверный флаг закрывает оба случая, и `meta` в V1-хранилище остаётся
нетронутым.

**4. Одноразовость токена держится на `INSERT ... SELECT`, а не на «UPDATE, потом INSERT».**
План предлагал сначала гасить токен, потом писать оценку. Тогда между двумя
операциями остаётся щель: если `UPDATE` не нашёл свободного токена, `INSERT`
всё равно выполняется, и спасает только `UNIQUE`. Сейчас условие «токен ещё
свободен» встроено в саму вставку:

```sql
INSERT INTO reviews (...) SELECT deed_id, reviewer_slot, ?, ?, ?
  FROM review_tokens WHERE token = ? AND used_at IS NULL AND ...
```

Ноль вставленных строк = кто-то успел раньше, и ответ 410. Гашение токена идёт
следом в той же транзакции. Проверено тестом с двумя одновременными сабмитами.

**5. Агрегация условна по статусу дела — иначе карма начислялась бы дважды.**
Плана «когда проходит второй INSERT» недостаточно: обе гонящиеся записи могут
увидеть «оценок стало две» одновременно. Поэтому начисление кармы и перевод
дела в `approved` идут одним батчем, и **оба** условны по прежнему статусу
дела — применится ровно одна пара. Уровень при этом считается от прочитанного
значения кармы: при совсем одновременных аппрувах он отстанет на шаг и
починится на следующем, а наружу всё равно считается из кармы.

**6. Перегенерация ссылки заменяет строку токена, а не добавляет новую.**
`UNIQUE(deed_id, reviewer_slot)` не даёт держать два токена на слот, поэтому
`send-review` делает `ON CONFLICT DO UPDATE`: старый токен перестаёт
существовать в ту же секунду. Живой токен переиспользуется, а не выдаётся
заново — иначе каждая отправка ломала бы уже разосланную ссылку.

**7. Бейджи при импорте считаются по сумме обеих шкал.**
Иначе бейджи за уровень («Хранитель», «Просветлённый») исчезли бы при переезде:
подтверждённая карма у мигранта нулевая. Бейджи — личные достижения, они не
влияют на рейтинг, и терять их незачем. На лидерборд это не влияет: там только
`karma_total`.

## Дев-режим: initData теперь подписывается по-настоящему

В V1 дев-мок подставлял `hash: 'devmode'` — проверять было нечем. В V2 Worker
валидирует HMAC на каждый запрос, и такой мок означал бы 401 на весь дев-режим.

Теперь `lib/telegram/init.ts` подписывает дев-initData локальным токеном
(тем же, что в `workers/.dev.vars`), и в браузере работает ровно тот же путь,
что в Telegram. Две детали, на которых это ломалось:

- **Поле `signature` обязательно**: без него SDK вообще не принимает
  `tgWebAppData`. На проверку HMAC оно не влияет — Worker пробует обе раскладки
  data-check-string, с ним и без него.
- **Строку нужно отдавать ровно такой, какой её подписали.** SDK разбирает
  initData в объект и собирает обратно сам; любая пересборка JSON юзера ломает
  HMAC. Поэтому подписанная строка запоминается в `devInitData()`, и клиент
  API в дев-режиме берёт её, а не то, что вернёт SDK.

`initTelegram()` из-за подписи стала асинхронной и возвращает один общий
промис: в дев-режиме React вызывает эффекты дважды, и второй вызов не должен
отвечать «готово» раньше, чем закончился первый.

## Что проверено

**Юнит-тестами** (`npm run test:api`, 22 проверки):

- валидация initData: подделанный hash, подмена `user` под чужой подписью,
  чужой бот, протухший `auth_date`, поле `signature`;
- пересчёт прогресса: счётчики, стрик, бейджи при создании дела и при аппруве;
- среднее двух оценок и округление половины вверх;
- восстановление стрика из истории V1 и слияние с текущим;
- алфавит токена ровно 64 символа и токены без повторов.

Последний тест появился не зря: в алфавите не хватало одного символа, маска
`byte & 63` вылезала за границу, и в токенах посреди строки оказывалось
`undefined`. Поймано на живой странице, а не тестом.

**End-to-end** (`npm run test:e2e`, 21 сценарий на живом `wrangler dev` + D1) —
всё, что перечислено в разделе «Верификация» плана, плюс:

- гонка двух сабмитов по одной ссылке → ровно одна запись в `reviews`;
- гонка двух последних оценок → карма начисляется один раз;
- чужое дело не открывается и ссылок на него не выдаётся;
- профиль друга не отдаёт `karma_self_total` и `telegram_id`;
- инвариант базы после прогона: карма каждого юзера равна сумме итоговых
  баллов его подтверждённых дел.

**В браузере** (Mini App на `next dev` + Worker + страница рецензента):

- запись дела → две ссылки → оценки 20 и 30 от «посторонних» → `+25`
  подтверждённой кармы в приложении;
- одноразовость: по использованной ссылке страница показывает «уже оценили»;
- импорт V1: 3 дела из localStorage → `+38` самооценки, подтверждённая карма
  не изменилась, дела помечены «Из прежней версии», повторный запуск ничего
  не задвоил;
- фолбэк share: вне Telegram ссылка кладётся в буфер и об этом сообщается.

**Не проверено:**

- живой Telegram: нативный share двух ссылок, deep-link `?startapp=f<id>`
  и добавление друга по нему;
- прод-деплой (Workers, Pages, Vercel) — ниже расписано, что для него нужно;
- два устройства под одним аккаунтом;
- поведение при сотнях дел: история грузится страницей в 50 записей,
  пагинация в UI не сделана (`hasMore` API отдаёт, экран его не использует).

## Чего нет намеренно

- **Rate-limit на маршрут ревью.** План допускал правила Cloudflare или счётчик
  в KV. Не сделано: KV ради MVP заводить не хотелось, а правила настраиваются
  в панели Cloudflare, а не в коде. Усреднение двух независимых оценок уже
  гасит накрутку одним человеком.
- **Cron, проставляющий `status='expired'`.** Как и планировалось, истечение
  проверяется лениво при чтении: автор видит «ссылка истекла» и жмёт
  «Создать ссылки заново». Статусы `expired` и `rejected` в схеме есть, но
  сейчас их никто не выставляет.
- **Удаление аккаунта.** Кнопка «Сбросить данные» из V1 убрана: она стирала
  CloudStorage, а данные теперь на сервере. Соответствующего endpoint'а нет.
- **Оптимистичный UI.** Запись дела — один запрос вместо трёх обращений к
  CloudStorage, пауза заметно короче, чем была в V1. Индикатор записи остался.

## Что нужно сделать руками для прода

Код готов, инфраструктура — нет. Ни одного секрета и ни одного `database_id`
в репозитории нет и быть не должно.

1. **База:** `npx wrangler d1 create karma-builder` → полученный `database_id`
   вписать в `workers/wrangler.jsonc` (сейчас там нули-заглушка) →
   `npm run db:migrate`.
2. **Секрет:** `npx wrangler secret put BOT_TOKEN --config workers/wrangler.jsonc`
   — настоящий токен из BotFather. Без него валидация initData не сойдётся.
3. **Worker:** `npm run deploy:api`. Запомнить выданный домен.
4. **Страница рецензента:** `cd reviewer && npm run build` → задеплоить `dist/`
   на Cloudflare Pages. В переменных сборки Pages задать
   `VITE_API_BASE_URL` = домен Worker'а. Файл `public/_redirects` уже отдаёт
   SPA по адресам вида `/r/<token>`.
5. **Обратно в Worker:** `REVIEW_BASE_URL` = домен Pages, `BOT_USERNAME` =
   username бота без `@` (из него собирается ссылка-приглашение в друзья).
   Оба — в `vars` внутри `workers/wrangler.jsonc`, затем повторный деплой.
6. **Mini App:** на Vercel задать `NEXT_PUBLIC_API_BASE_URL` = домен Worker'а
   и передеплоить. `NEXT_PUBLIC_DEV_BOT_TOKEN` в проде **не задавать**:
   дев-мок в production-сборке всё равно выключен.
7. **Проверить в живом Telegram** пункты из «Не проверено» выше.

Порядок именно такой: Worker должен знать домен страницы рецензента, а та —
домен Worker'а, поэтому один из них деплоится дважды.
